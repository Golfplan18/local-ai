Every affected surface needs an explicit independent-review verdict: the reviewer compares behavior with its owning canonical section, or, when behavior truly does not change, expressly accepts exactly one `Documentation-No-Impact: <surface-id>` trailer in the affected repository's final task commit. Regenerate every registered body-only mirror or site derivative from the canonical before verification.

It must never infer matching worktrees or fall back to live checkouts. The deterministic result is mechanical: it proves only declared ownership, typed references, lifecycle state, task dispositions, accepted-finding boundaries, and registered propagation. Independent review owns semantic truth.

The independent reviewer receives the complete evidence packet: all five cumulative repository diffs, any unversioned global-instruction and programming-skill changes, affected surface identifiers, exact canonical-section changes, every no-impact trailer and rationale, propagation results, verbose gate output, and the exact authorized test output. Missing evidence is not acceptance, and the reviewer gives an explicit accept or reject verdict for every affected surface.

The managed hook set is active and verified across all five repositories: one blocking local `pre-push` hook per repository, plus fail-open local `post-commit` framework-pair audit hooks in Ora and the vault. Any post-gate correction invalidates the result. Before the first merge, every remote task branch and pull request must exist and be ready, propagation must be complete, and the combined gate and review must have passed. Otherwise merge nothing. ## Project Plugin Convention (READ BEFORE ADDING APPLICATION CODE)

**Ora is a generic prototype. Project-specific code does NOT belong in `~/ora/`.** When you find yourself writing code that references a specific project (FRED API calls, MSI's article schema, a particular publication's content collection, anything else that won't be useful in a fork), that code goes in the project's directory at `~/sites/<project>/ora-project/tools/` — never in `~/ora/orchestrator/`.

The mechanism is documented in `~/Documents/vault/Projects/Ora/Reference — Ora Project Plugin Convention.md`. Briefly:

- A project lives anywhere on disk in a directory containing an `ora-project.json` manifest.
- The manifest declares `tools` (project-specific Python helpers), `slash_commands` (chat-facing), `frameworks`, `peds`, `workflow_specs`, `chromadb_collections`, `capability_slots` (project-defined visual-capability slots merged into `capability_registry.py` at registry load — see Plugin Convention v1.2 §12), `themes` (project-shipped chat-UI themes merged into the V3 server's theme index at startup — see §13), and `framework_configurations` (named configuration profiles for framework specs, with `${config.*}` substitution + extension-point overlay splicing at framework invocation time — see §14).
- Projects register with Ora by writing a pointer file at `~/ora/data/projects/<nexus>.json` — manually, programmatically, or via the `/project-register <path>` slash command.
- Ora invokes project tools via `~/ora/orchestrator/project_registry.py::invoke_project_tool(nexus, name, args=...)` — subprocess with JSON-on-stdout contract, with `ORA_HOME` / `ORA_VAULT` / `ORA_PROJECT_NEXUS` / `ORA_PROJECT_ROOT` set in the env. The `/project-tool`, `/projects tool`, and project-declared slash-command adapters route through the existing Paused one-shot protection path and bind project, manifest, command, interface, executable/script, and argument identities by digest before execution.
- Frameworks reference tools by abstract name (`news-related-find`, `news-index`), never by file path. The dispatcher resolves at runtime against the registered project's manifest.
- Project tools that need to call a model use `~/ora/orchestrator/model_dispatch.py::invoke_chat(system_prompt, user_prompt, slot=...)` — the project-facing API to Ora's existing routing. Slots: `breadth` (default; high-context generative), `depth`, `sidebar`, `consolidator`, `evaluator`, `step1_cleanup`, `classification`. Project tools never hardcode specific models; they declare slot preference and the publisher's `routing-config.json` decides.

**Reference implementation:** `~/sites/mainstreetindependent/ora-project/` (Main Street Independent). When considering where a new piece of project-specific work should live, mirror what MSI does there.

The `/project-tool`, `/project-list`, `/project-register`, `/project-unregister` slash commands provide the chat-facing inspection and invocation surface; they are project-agnostic and live in `~/ora/orchestrator/slash_commands.py`.

## Repository Overview

Ora is a multi-model orchestrator for local LLMs on Apple Silicon. It runs an 8-step adversarial pipeline with configurable "Gears" that route prompts through cleanup, context assembly, analysis, cross-evaluation, revision, and verification stages.

**Hardware:** Apple M4 Max, 128 GB RAM, macOS 26.3

**Local Models (vision-capable lineup, 2026-05-26 swap — three training families: Qwen / Zhipu / Mistral):**
- **Utility (4B):** Huihui-Qwen3.5-4B Claude-Opus-abliterated (4-bit) — 4 GB, dense, vision-capable. Classification, step1 cleanup, RAG planning.
- **Campaign baseline (9B):** Qwen3.5-9B Vision (4-bit MLX) — 7 GB, dense, vision-capable. Powers the `qwen-9b-only` configuration; the file that drives the "reproducible on $1K consumer hardware" demonstration.
- **Fast slot (27B):** Qwen3.6-27B Vision (4-bit) — 17 GB, dense, vision-capable. Sidebar / step1 cleanup / RAG planning at higher quality than the 9B.
- **Large local A — Qwen 122B MoE:** Qwen3.5-122B-A10B (mxfp4) — 62 GB, MoE (~10B active per token), vision-capable. Fast inference relative to dense equivalents.
- **Large local B — GLM 4.6V MoE:** GLM-4.6V (mxfp4) — 58 GB, MoE (128 routed + 1 shared experts, 8 active per token, ~11B active), vision-capable. Zhipu-family alternative for cross-family adversarial pairing.

## Architecture

### Pipeline (boot.py — the orchestrator)
1. **Step 1** — Phase A (prompt cleanup) followed by the **four-stage pre-routing pipeline** (Phase 9, replaces the retired Phase A.5):
   - **Stage 1 — Pre-Analysis Filter:** substring-matches the prompt against the signal vocabulary registry and a short bypass-trigger list. Greetings, simple lookups, and prior-conversation references bypass the analytical pipeline; analytical-artifact triggers forward to Stage 2.
   - **Stage 2 — Sufficiency Analyzer:** classifies signals as strong vs weak, AND-composes them, detects conflicts, runs cross-territory adjacency check, runs within-territory disambiguation, applies the friction reducer (skips questions the prompt already answered). Either dispatches a `mode_id` or surfaces a single plain-language disambiguation question per the Disambiguation Style Guide.
   - **Stage 3 — Input Completeness Check:** loads the dispatched mode's `input_contract`, picks `expert_mode` vs `accessible_mode`, scans for required fields, and either elicits the missing input or offers graceful degradation to a lighter sibling.
   - **Stage 4 — Mode Execution:** loads the runtime config (errors safely if missing per Decision C), composes the educational-parenthetical dispatch announcement, then runs the gear pipeline. The four-stage pipeline lives in `boot.py::run_pre_routing_pipeline`; supporting registries are read from `~/ora/architecture/`.
2. **Step 2** — Context assembly: mode file, conversation RAG, concept RAG (ChromaDB)
3. **Steps 3-8** — Gear-appropriate execution:
   - **Gear 1-2**: Single model, direct response
   - **Gear 3**: Sequential adversarial (Depth → Breadth eval → revise → verify, up to 2 correction cycles)
   - **Gear 4**: Parallel adversarial (ThreadPoolExecutor — parallel analysis, cross-eval, revision, consolidation, verification)
4. **Output routing** — Screen, file (with vault YAML frontmatter), or both

### Meta-Layer Oversight Subsystem (2026-05-04)

Since 2026-07-02 the workflow spec sweeper deduplicates drift emission and handles stale registrations. Drift on an existing spec (missing corpus template, missing PFF/OFF files, parse failure) emits once per distinct issue signature, not once per sweep; a resolved-then-recurring or changed issue set re-emits. A registration whose (non-empty) spec path has vanished emits the drift event on the first missing sweep, then auto-deregisters once BOTH gates are met — ≥3 consecutive misses (`ORA_WORKFLOW_SWEEPER_MISSING_SPEC_SWEEPS`) AND ≥10 min since the first miss (`ORA_WORKFLOW_SWEEPER_MISSING_SPEC_MIN_SEC`; both provisional): the pointer is archived as `workflow-pointer.json.deregistered` and a log-only `WorkflowWatcherDeregistered` event records the drop. The self-heal lives in the sweeper itself: every sweep rechecks tombstones and restores any whose recorded spec path exists again (log-only `WorkflowWatcherReregistered`), so a false-positive drop recovers mid-process without a daemon restart and regardless of where the spec lives. Sidecar state (`sweeper-state.json`, written atomically) is bound to the pointer's `registered_at`, so a re-registered workflow never inherits an old episode's counters, and the missing-spec episode and persistent-drift dedup are kept in disjoint single-family records so a blink can't leave stale counters that later bypass the gates; corpus-only registrations (blank spec path) produce a clean report — no drift event, never deregistered (the sweeper has no jurisdiction over a spec-less registration); `sweep()` without an emitter is observation-only (persists nothing, writes no heartbeat), and the module's CLI runs in that mode so a manual smoke test never mutates live state. ### Trigger Surface (2026-08-22)

The authoring and inspection layer over the exact-event / exact-deadline substrate — `orchestrator/triggers.py`, `/trigger` in `orchestrator/slash_commands.py`, eight `/api/triggers*` routes in `server/app.py`, and the **Scheduled** group in the V3 sidebar's Oversight supergroup. It replaces capability lost as collateral damage on 2026-08-05: `519294b1` removed the governed-Process kernel and `process_triggers.py` went with it, leaving a live `DeadlineQueue` that could only be filled by writing Python and no screen anywhere showing what was scheduled, what fired, or what failed. It is **not** a return of that kernel — the deleted G1.19 implementation was ~1,400 lines over a ~20,000-line dependency and carried its own clock; this is a thin layer that adds no engine.

- **A Trigger is a separately authorized activation object.** It never modifies the thing it activates and never executes work itself. `data/triggers/triggers.json` (one consolidated file, atomic write + `flock`, path resolved at call time from `runtime_paths.DATA_DIR_STR`) is the only durable object added: it holds the specification plus `status` / `approved_spec_digest` / `approved_action_binding` / `armed_deadline_key`. Firings are **not** stored here — they are `runtime_hygiene.EventLedger` records of type `trigger_firing`, which is where idempotency, append-only evidence, size-based rotation, and restart recovery already live.
- **Four causes, compiled to the framework's two primitives.** `calendar` arms exactly one `DeadlineQueue` record for its next occurrence (`trigger_calendar`, handled in `oversight_daemon._handle_trigger_calendar_deadline`) and arms the successor from the persisted contract. `file_change` is one guarded branch in `runtime_event_dispatcher.dispatch_paths`. `trigger_completion` fires from the ledger's own `completed` transition (cycle-checked at create and update). `manual` is an explicit human request. **No interval scanner, sweep, cron, launchd unit, or clock fallback.**
- **Three action kinds, all exact and bounded.** `project_tool` → the exact Project adapter into `project_registry.invoke_project_tool`; an active Trigger uses revocable standing authority bound to that exact Trigger specification and the full resolved Project root, manifest, command, executable/script, interface, and arguments/stdin identity, while a manual run from a draft or paused Trigger uses the existing Paused one-shot approval and receipt path. `framework` → `milestone_executor.execute_framework`, restricted to `framework_invocability.is_user_invocable_framework`; and the single G1.21 `email_send` action → Persona-disclosed Fastmail/JMAP delivery through the existing Paused one-shot approval and receipt path. Email is manual-only: its exact message is inspectable before provider contact, the configured global sender and recipient allowlist are bound into the approval identity, and rollback cancels only before provider contact. Telegram, inbound email, generic channels, and post-send recall remain unavailable. A **literal command string is deliberately not an action kind**: an opaque command is honestly `irreversible` mutability, which `tool_events.gate()` blocks, and classifying it as `external_write` to slip past would be an overclaim. Declare the script once in an `ora-project.json` manifest instead — that is the Plugin Convention path and it costs no new execution authority.
- **The Runtime Principle is enforced, not requested.** A `calendar` Trigger is refused at create and again at activate without a written `runtime_justification` of ≥ 40 characters, which is rendered verbatim in the activation review and on the card. G1.19 also demanded four fixed boilerplate sentences the user retyped; those are now one rendered, non-editable disclosure (`triggers.INTERMITTENCY_NOTICE`) because app intermittency is a property of the runtime, not of any one Trigger.
- **An event surface that could never fire is refused.** A `file_change` selector must resolve inside a live watch root — derived from `runtime_event_dispatcher._roots()`, the same accessor the handler uses, never a second literal — and must survive `_actionable()`. Today that means the vault and `~/Documents/Ora Resources`; a selector under `~/ora` is refused with the reason instead of silently never firing.
- **Activation approves one exact specification and resolved action contract.** `GET /api/triggers/<id>/review` returns the rendered request plus an activation wire field named `spec_digest`; despite that historical name, the digest binds both the normalized Trigger specification and the full resolved action contract, including exact Project program/input identity or composed Framework file and Project nexus/profile context when applicable. Activation carries that combined digest or is refused. The same public contract is stored as `approved_action_binding` and re-resolved before every firing: drift records `action_definition_drifted` and runs nothing. Editing is draft/paused only and always returns the Trigger to draft.
- **Firings never run on the lanes.** The deadline lane also serves `daily_note`, `log_retention`, and thousands of trace expirations, so a claimed firing is handed to a short-lived daemon thread; a per-trigger in-process lock records `skipped_overlap` instead of double-running. A pre-start failure may close once the absent wrapper proves action work never began, and Windows retains its authenticated Job Object terminal proof. On POSIX, however, a deadline reached after the action-start barrier terminates and verifies the known process group but cannot disprove that a descendant created a new session and escaped it. That firing therefore remains claimed as `termination_unacknowledged`, leaves its protected start and overlap guard nonterminal across restart, and blocks another firing even when the recorded wrapper and group are absent.
- **The panel states what it cannot promise.** The Scheduled list carries a lane-health banner when `oversight_daemon.runtime_health()` reports the deadline lane down or flapping (a lane the watchdog keeps resurrecting passes every liveness check — 2,257 unreported crashes before 2026-08-16), and one footnote counting the deadlines Ora arms for itself (2,141 at time of writing, almost all `trace_retention`) rather than burying two Triggers under them.
- **Substrate additions**: `EventLedger.list_events(event_type=…)` and `DeadlineQueue.pending_counts()` — read accessors on existing classes, not a parallel reader.
- **Tests**: `orchestrator/tests/test_triggers.py` (63) + `server/static/ora-visual-compiler/tests/cases/test-sidebar-triggers.js` (18 assertions).

### Standalone Programming (2026-08-05)

Programming is an explicit repository-work path implemented in `orchestrator/programming.py`, `server/app.py`, and `server/static/js/programming.js`. It does not use Codex or Claude Code transports and does not route ordinary `/chat` or `/chat/multipart` traffic.

The flow is: accept a repository name or path; inspect repository instructions, implementation, tests, Git state, and automation; ask at most two rounds of three material questions; propose one concise plan; wait for `approved: true`; create an `ora/` task branch; execute coherent milestones with real repository tools; send the raw diff to a fresh reviewer; correct `FIX`; commit each accepted slice; require final `DONE`; then perform only the approved local/push/PR/merge finish line. Documentation-impacting work is the exception at the final boundary: after milestone commits it pauses for a freshly generated five-root packet, final review binds each exact submitted diff and explicit task branch to the live gate state, and `DONE` returns all five reviewed local branches without invoking Programming's ordinary single-repository finish. A DCP `local_commits` plan stops there; only `coordinated_dcp` authorizes the five-repository coordinator to land those exact heads.

The reviewer receives no executor transcript or claims. It can independently run repository checks, fetch authoritative outside sources, and directly inspect image bytes or rendered PDF pages. Its first line is exactly `CONTINUE`, `FIX`, `DONE`, or `ASK USER`. DCP evidence is supplied only to cumulative `FINAL` review; a final correction consumes that packet and requires a new gate before review resumes.

Git is the state and rollback mechanism. Do not add Programming Run, artifact, event, receipt, lifecycle, trigger, automation, process-library, checkpoint, or recovery persistence. Preserve safely separable pre-existing work; return `ASK USER` only when task work and user work cannot be separated safely.

### Execution Review Subsystem (2026-07)

Turns Ora from a text-critique engine into a **closed-loop controller over non-self-evidencing outputs** — results whose correctness depends on reality outside the returned message (a code change, a fact-checked claim, a published page). Such outputs are judged on **mechanically generated evidence**, never on the executor's own report. Canonical spec: the build spec handed in at implementation time (`ora-execution-review-spec.md`); durable session state: `data/execution-review-design-record/HANDOFF-execution-review.md` (moved into the repo 2026-08-14 when `~/ora-worktrees/` was deleted; the 650 MB of duplicate repo copies beside it were discarded, the 102 design files kept). **The loop is LIVE**: the canonical foreground launcher `run-ora-server.sh` exports `ORA_EXECUTION_LOOP=1` (default OFF in code; flag-OFF is byte-identical to the pre-loop path), and both `start.sh` and the macOS launchd service delegate to it. Built across Phases 1–8; all landed on `main`.

- **Tool instrumentation + capability gate** (`orchestrator/tool_events.py`, `config/capabilities.json`): every tool/action is recorded independently of the model's narration (the source of the two dispatch signals — what changed, what was read *as a source*). Four mutability categories (`read` / `reversible_write` / `external_write` / `irreversible`) × a sensitivity axis (`public` / `private` / `sensitive` / `secret`). `gate()` runs BEFORE execution and independently of the permission mode: unknown / irreversible / secret / (model-facing) sensitive **fail closed** (default `mutability=irreversible`, `sensitivity=secret`), deny-then-queue a Paused entry, unlocked only by a one-shot approval token or a live human. `secret` never enters a packet; `sensitive` is always redacted from durable storage.
- **Shell policy** (`orchestrator/tools/bash_execute.py`): an opaque shell command can't honestly carry one capability, so it is allowlist-with-profile (known verbs get their profile) OR sandbox-and-observe; anything unrecognized — including `source`/`.`/`eval`/`bash x.sh` (they execute file contents) — **fails closed**. Tests: `test_shell_profiles.py`.
- **Risk gate + two clocks** (`orchestrator/risk_gate.py`, `dispatcher.py`): risk tier is estimated up front (conservative, user-overridable); routing is decided AFTER the run from the observed signals. Post-hoc routing is permitted only inside REVERSIBLE tiers — irreversible actions are classified and gated BEFORE the executor runs.
- **Polymorphic packet + renderer** (`orchestrator/execution_packet.py`): `ExecutionPacket` alongside `TextArtifact`; `evidence_lanes` (mechanical, real verdict) and `judgment_lanes` (interpretive, `verdict: null` by construction) are structurally separate. `render_for_review` presents mechanical evidence FIRST and the producer claim LAST, explicitly labeled an unverified claim — this is where "evidence over claims" is physically enforced.
- **Evidence catalog + runner** (`orchestrator/evidence_runner.py`, `.ora/evidence.yaml`): the repo/project catalog declares WHICH checks exist and HOW they must run (fixed working-dir, timeout, network policy, env isolation, `mutates` flag, redaction) — so the executor cannot choose its own proof at runtime. The task-specific **Evidence Contract** is produced at planning time. A green run means "nothing broke that you knew to check", NOT "solved the right problem" (only the planning criteria + adversarial verify catch a wrong-problem solution). Enforce-or-refuse: off macOS/Linux with no enforcing sandbox backend, a mutating/network check **refuses rather than running unenforced**. POSIX shell needs a real `ORA_POSIX_SHELL` (never `cmd.exe`); three dirty-state modes (`clean_worktree` / `review_dirty_diff` / `continue_user_changes`).
- **The loop** (`orchestrator/execution_loop.py`): plan → single-writer execute → mechanical capture → dual-family verify → revision router → stop-or-escalate. Findings are tagged plan-level vs execution-level (route back to planners vs executor). Verify uses a DIFFERENT model family (single-family degrades confidence + escalates high-risk to a human). Stop when criteria pass and no high-severity finding remains, else escalate at a fixed iteration count with the packet — never churn. Escalation lands the abandoned attempt on an inspectable, unmerged, per-turn branch (§13). First landing runs `actuator=None` (failed verifies escalate rather than self-revise); mutating checks run in an isolated disposable worktree (kill-switch `ORA_EXEC_REVIEW_MUTATING`).
- **Isolated mutating-check actuator** (in `evidence_runner.py`): a mutating check never contaminates the user's worktree/index/refs/history. `tree_commit_at` is a REF-LESS commit of the dirty tree via a throwaway `GIT_INDEX_FILE` + `commit-tree`; `create_isolated_worktree` / `remove_isolated_worktree` are containment-guarded (refuse any non-scratch path) with `git worktree prune` owner-resolution so a ref-less snapshot is never left GC-pinned.
- **Tiered persistence** (`orchestrator/execution_persistence.py`): `git_only` (default) / `ledger_line` / `durable_note` — promote to durable only when escalated, failed-to-converge, or carrying a plan-level finding. **Redaction FAILS CLOSED**: if the redactor can't produce a provably-scrubbed copy it returns None and every durable write is withheld. Stealth turns write no durable residue; the store `data/execution-records/` is git-ignored (true zero-residue on a stealth purge).
- **Adapter families** (`orchestrator/execution_families.py`, `.ora/tools/`): the five evidence classes (diff+validate / run+observe / render+inspect / deploy+probe / collect+provenance) are adapter *families* + declared recipes, not one-class-one-adapter. `deploy_probe` (tri-state PASS/FAIL/INDETERMINATE + mandatory rollback), `render_inspect` (unrun → owed, not failed), vault checks (`vault_frontmatter_lint.py`, `vault_wikilink_check.py`, `render_validity.py` — stdlib-only, shell-free). Vault-side `.ora/` lives in the Obsidian-vault repo, scripts byte-identical to the ora canonicals.
- **Provenance lane** (`orchestrator/execution_provenance.py`): the tool-event log proving a source was *contacted* is necessary but not sufficient — a `collect_provenance` claim additionally needs a claim-to-source map (excerpts + timestamps). A content-withheld sensitive source proves "consulted" but is never citable as support ("consulted ≠ used correctly").
- **Programmatic seam** (`orchestrator/execution_review.py`): `record_program_run` runs the same packet gauntlet for a run that never flows through `run_pipeline`/`server` (signals folded from the run's own tool-event log; `enforcement_model` caller-mandatory + validated + refuse-on-invalid so a boundary-observed run can't overclaim per-call gating).
