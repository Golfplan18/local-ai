STRUCTURAL DEFINITION. A tornado is a sorted horizontal-bar SENSITIVITY chart for one outcome. ONE fixed outcome metric varies as each input is swung low→high independently while all others hold at base. Each input = one horizontal bar spanning [outcome_at_low, outcome_at_high], crossing a single shared vertical reference line at base_case_value. Bars stack widest-on-top → narrowest-bottom, producing the funnel ("tornado") silhouette. Required spec fields: base_case_label, base_case_value (number, the center line), outcome_variable, outcome_units, parameters[] (each: label, low_value, high_value, outcome_at_low, outcome_at_high; optional low_label/high_label), sort_by ∈ {swing|high_impact|custom}. NEVER "alphabetical" (invalid enum).

WHEN THIS vs THE SIBLING. The canonical degradation is decision_tree / VOI tree — the analyst is asked "which uncertainty matters most?" and reflexively models the DECISION (commit/hedge/defer branches, chance nodes, EVs, "which variable to research"). Disambiguating cue: a tornado RANKS the sensitivity of inputs around a fixed base case; it makes NO choice, has NO branches, NO probabilities, NO payoff folding. If the task names inputs to rank by impact on one number → tornado. If it weighs ALTERNATIVE ACTIONS under uncertainty → decision_tree. Emit type "tornado", NOT a tree.
