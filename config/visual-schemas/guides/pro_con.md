**Structural definition.** A `pro_con` spec is a degenerate argument map (Protocol §3.13, ARGUMENT family, "constraint-mapping" mode): a single root `claim` with two sibling arrays, `pros[]` and `cons[]`. Each entry is an `argument` object: required `text`, optional `weight` (integer 1-5), optional `source`, optional `children[]` (same `argument` shape, recursive). Optional top-level `decision`. The compiler lays this out as a TWO-COLUMN tree — pros left (green), cons right (red) — with weight badges and nested sub-branches drawn as indented children. `additionalProperties:false` everywhere: NO keys beyond claim/pros/cons/decision and text/weight/source/children.

**THIS type vs. siblings.** Use `pro_con` for a single decision evaluated as for/against an explicit claim. Use `ibis` instead when you have issues→positions→arguments with typed support/object edges and multiple competing positions (warrant ≠ evidence grammar enforced). Use `decision_tree` when chance/probability and payoffs matter. pro_con is the LIGHTEST argument form — one claim, two lists.

**The exact failure modes from the judge (defeat all four):**
1. *Missing-bucket / incompleteness.* Judges docked every lane for dropping a requested category. Lesson: cover the claim's real trade-space. Populate BOTH `pros` AND `cons` substantively (3+ each here). Never emit an empty array or a one-item side.
2. *No sub-branches.* The richest lane scored highest precisely because it drew nested `children`; flat lanes lost points. Use `children[]` on at least your heaviest pro and heaviest con — terminal leaves with concrete, checkable `text` (no further weights needed on leaves).
3. *Decision footer overclaims / contradicts prose.* Judges flagged a `decision` that asserted more than the arguments support. Keep `decision` calibrated and conditional — defer to the open risk, do not declare victory.
4. *Garbled CJK / mixed-script glyphs.* Keep all `text` in clean ASCII/Latin; avoid pasted non-Latin glyphs the renderer mangles.

**Layout + labeling rules.** Aim for BALANCE — comparable count and total weight on each side so neither column visually dominates by accident (here both sides sum to 12). Weights are integers 1-5 ONLY (the canonical invalid fixture used 9 — schema rejects >5). Keep top-argument `text` to a short legible clause (~8-12 words); push detail into children. Max nesting depth 2-3. `semantic_description`: level_1 names it as a two-column pro-con tree with counts/encodings; level_2 gives the weight sums/extrema; level_3 the perceptual tension and what the decision turns on; `short_alt` ≤150 chars describing THIS tree (claim + the balance), never "bar chart" boilerplate. Set `relation_to_prose:"integrated"`, `mode_context:"constraint-mapping"`.
