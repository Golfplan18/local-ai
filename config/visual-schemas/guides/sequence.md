**Structural definition.** A `sequence` is a UML sequence diagram in the PROCESS family, rendered Path A from a Mermaid `sequenceDiagram` string. It shows *time-ordered message exchange between named participants (lifelines)* — WHO sends WHAT to WHOM, in what order. Vertical axis = time (top→bottom). `spec.dialect` MUST be the const `"sequence"`; `spec.dsl` MUST be a valid Mermaid `sequenceDiagram`. mode_context `"process-mapping"`.

**Sequence vs. its confusable siblings.** Use `sequence` when the answer is an *interaction protocol* — distinct actors passing messages over time (auth handshake, checkout, API call chain, escalation). Use `flowchart` instead when it's one actor's decision/branch logic (diamonds, no message passing). Use `state` when it's one entity's lifecycle (statuses + transitions, no second party). The #1 degradation is a sequence collapsing into a flowchart: if you find yourself drawing decision diamonds or a single swimlane of steps with no sender→receiver arrows, you've left the type.

**Failure modes from judge notes — defeat these exactly:**
1. *Conditionals narrated, not drawn* (cost the top render its points). DRAW branches as Mermaid `alt`/`else`/`opt`/`loop`/`par` combined fragments inside the DSL. Never describe "if approved… otherwise…" in prose while the diagram shows only the happy path.
2. *Duplicate/orphan dangling lifeline* (qwen9b). DECLARE every participant once, up front, with `participant X as Label` / `actor X`. Use the SHORT alias on every message. Never introduce a participant implicitly mid-diagram or with two spellings — that spawns a ghost lane.
3. *Cramped wide render.* Keep it ~5 lifelines and ~15 messages; legible-dense beats sprawling.

**Concrete layout + labeling rules.** Open with `autonumber` (judges reward numbered messages). Declare 4–6 participants top-to-bottom-left-to-right, the human as `actor`. Solid `->>` for requests/calls, dashed `-->>` for returns/responses. Use a self-message (`API->>API: validate`) for internal work. Add 1–2 `Note over`/`Note right of` for out-of-band context. Every arrow needs a sender, a receiver, and a verb-phrase label. §7 invariant: *every message has a sender and receiver* — no danglers. Realistic scenario, concrete values (amounts, status codes). `relation_to_prose: "integrated"`.

**semantic_description** must reference THIS interaction: level_1 names the lifelines + reading direction; level_2 counts lifelines/messages and names fragment types; level_3 describes the visual fork/loop shape; short_alt ≤150 chars naming actors + branches (never "bar chart").
