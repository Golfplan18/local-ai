STRUCTURAL DEF. A c4 is NOT a node-link graph. `spec.dsl` is **Structurizr DSL** (Path A, SPATIAL family); `spec.level` ∈ {`context`,`container`} only — `component`/`code` are schema-rejected (§3.16). DSL has two sections: `model {}` declares TYPED elements — `person "Name" "desc"`, `softwareSystem "Name" "desc"`, and (container level only) `container "Name" "desc" "Technology"` nested inside `softwareSystem { … }` or a `softwareSystemBoundary`. Relationships are `src -> dst "verb phrase" "Technology/protocol"`. A trailing `views { systemContext sys / container sys { include * autolayout } theme default }` block selects the single view. The renderer draws people as stick-figures, systems/containers as labeled boxes (name + type + tech tag), a dashed boundary around the system, and arrows with description+technology — THIS notation IS the deliverable.

WHEN c4 vs SIBLING. Build c4 only for software/system architecture (services, datastores, external SaaS, users). The trap is degrading into a generic `concept_map`/`flowchart` of ellipses+arrows. Disambiguating cue: if entities have software *types* (a person, a system you own, an external dependency, a datastore) and edges carry a *protocol/technology* — it's c4. If it's abstract concepts or process steps, it's NOT c4.

JUDGE FAILURE MODES DEFEATED. (1) **Over-aggregation into blobs** ("all actors→one node, all externals→another"): declare EVERY entity individually — each user role its own `person`, each external SaaS its own `softwareSystem`. (2) **Not-true-C4 ellipse/arrow style**: emit real Structurizr keywords (`person`/`softwareSystem`/`container`/boundary/tech tags), never a bare edge list. (3) **Dropping/inventing entities**: include exactly the entities in the prose, name them verbatim, no invented "External Gateways".

LAYOUT/LABELING. Every element gets a one-line description; give each `container` a Technology so its box reads `[Container: <tech>]` (the C4 hallmark). Mark every third-party/external system with `{ tags "External" }` — the renderer styles it as a muted box labelled `[Software System — External]` and places it OUTSIDE the system boundary. Container level: nest owned `container`s inside the `softwareSystem { … }` block — the renderer draws the dashed system boundary around them and auto-scopes the view to the system that HAS containers, so a `views { }` block is optional (declare one only to pin a specific scope/layout). Each relationship gets a verb phrase. Keep ≤ ~12 elements/view; split levels rather than mixing. NEVER mix context and container elements in one view.
