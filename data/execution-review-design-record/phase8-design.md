### 2.4 The map builder — two levels

At the terminal, for BOTH the source-read-only branch AND mixed mutation+source-read turns (the mixed case gets a filler call today's owed branch never gives it — scout-confirmed gap):

**Source registry.** One entry per source: `{source_id, kind: web|vault|conversation|graph|file|mcp|tool, ref, title?, retrieved_at?, content_hash?, sensitivity, excerpt, injected}` built from: `web_source_chunks` + `claim_evidence` chunks (rich; URL + snippet + timestamp); step-2 candidates (vault/conversation doc identity — from `context_pkg` additions or `step2-context.json` via `trace_dir`); `tool_results` (deterministic-tool outputs); dispatcher-recorded `file_read` events (path + hash from the turn-local event log). Local files MAY be re-read post-hoc for excerpts (cheap, not web): re-read is verified against the recorded `content_hash` — mismatch ⇒ excerpt withheld + `content_changed` flag (never quote a file the turn didn't see). MCP sources: registry entry with `kind: mcp`, NO excerpt possible (boundary-only, no reads[]) — honestly marked `opaque: true`. **⚖ Rev 3 refinements (critic):** (i) `injected: true|false` — `format_web_context` truncates `all_chunks` by `max_chars` ([web_consultation.py:973-991]), so the retained chunk list can be a SUPERSET of what actually entered any prompt; the formatter additionally returns the included-chunk ids (additive), and only `injected: true` sources may support a claim (a map that cites material the model never saw would be fabricated provenance). (ii) `retrieved_at` falls back to the recording EVENT's `ts` when the chunk carries none, else is omitted AND counted in `coverage.missing_timestamps` — never fabricated (§4 requires timestamps; absence is disclosed, not invented). (iii) A secret-classified source is recorded as `{kind, sensitivity: "secret"}` ONLY — no `ref`, no `what`, no hash: existence-only, mirroring `_redact_for_record`'s secret rule.

**Excerpt scrubbing at BUILD time, keyed on per-source sensitivity:** web/public → `scrub_content` + kept (capped); vault/private → `scrub_content` + kept (capped); sensitive paths (via `resolve_path_sensitivity`) → `[SENSITIVE: N chars]` descriptor, no content; secret → never enters the registry at all (existence marker only). **Level 1 — mechanical (always, no new model calls):** claims = the union of step-4.5 flagged claims + V8 unflagged claims (each ALREADY carrying per-claim evidence chunks — the map for these is verbatim reuse of `per_claim_evidence`). Every map row therefore carries `support_status: supported | unsupported | unassessed`: `supported` only where an affirmative judgment exists (Level-2 mapper verdict, or a step-4.5 evidence row whose verification outcome affirms the claim); retrieval-only rows are `unassessed`, retrieval-that-contradicts is `unsupported`. Coverage stats: `{claims_total, claims_mapped, claims_supported, claims_unsupported, sources_total, sources_used, sources_unused, opaque_channels, missing_timestamps, truncated}` — where **at Level 1 `claims_total` is `null`** (the deliverable's claim universe is unknowable without the Level-2 extractor; flagged+unflagged counts are reported as `claims_examined` instead, never presented as the total).

**Level 2 — model-assisted (flag-gated, default OFF at first landing):** a single small-model pass (the `_detect_conflicts_against_vault` pattern: indexed source blocks in, structured claim→source refs + per-claim support verdicts out) that (a) extracts remaining claims from the FINAL deliverable (the V8 extractor prompt is the prior art), (b) maps them to registry entries, and (c) judges support. **Post-hoc `source_read` confirmation (§7 finally lands):** every candidate read whose source appears in `sources_used` is stamped `confirmed: true`; used-nowhere candidates get `used: false`. `execution.source_reads` entries gain these two fields (additive; the public-safe shape is unchanged otherwise). **Sufficiency (⚖ Rev 3 — rewritten; the critic proved the Rev-0/2 formula self-contradictory and false-True-capable at Level 1):** `lane.sufficient = True` iff **`claims_total` is a real number (Level-2 extraction ran)** AND `claims_total > 0` AND **every claim is `support_status: supported`** (mapped-but-unassessed or unsupported ⇒ not sufficient) AND no opaque channel contributed unaccounted (an MCP-sourced turn can at best reach `False` + honest `opaque_channels` — consulted ≠ used correctly cannot be verified through an opaque boundary, §17). **Level 1 alone can NEVER produce `sufficient=True` by construction** (`claims_total: null` fails the first conjunct) — it records `False` with a real partial map + honest coverage, an upgrade over today's permanent `None` without ever manufacturing a green light from retrieval-presence.

## 3. Design pillar 2 — the isolated mutating-check actuator (Chunk B)

### 3.1 Lifecycle (new primitives in `evidence_runner`, generic)

```
prepare:  delta_commit = temp-commit of the CURRENT tree parented at base_sha
          (the create_escalation_branch throwaway-index idiom, refactored into a
          shared helper `_tree_commit_at(repo_root, base_sha) -> sha` — GIT_INDEX_FILE
          + read-tree base + add -A + write-tree + commit-tree; user HEAD/index/tree
          UNTOUCHED; captures untracked files, which delta_ref does NOT)
create:   wt = git worktree add --detach <scratch>/exec-review-wt/<id> <delta_commit>
run:      run_contract(catalog, {"required_standard_checks": deferred_mutating},
                       repo_root, worktree=wt, mode="clean_worktree")  ← existing machinery
          (⚖ Rev 3: exact contract key — the loop's own filtered-contract idiom, execution_loop.py:332)
merge:    replace the skipped deferred CheckResults in cr.results with the real ones;
          re-run fill_evidence_lanes + contract_sufficient (unchanged functions)
remove:   git worktree remove --force <wt>; git worktree prune; rmtree fallback
          (finally-guaranteed; plus a best-effort orphan prune at actuator start)
```

**Why materialize at `delta_commit` instead of spec-literal "worktree at base → apply delta":** `git apply` of `evidence-diff.patch` silently loses untracked new files (hand-verified: `snapshot_after` diffs `<base>` — tracked changes only) and adds a fragile patch-application failure mode. `worktree add --detach <delta_commit>` produces the exact post-execution tree with the pre-exec base as parent — same isolation, higher fidelity, one less moving part. The spec's intent (run mutating checks against the turn's delta in a disposable tree, never the live checkout) is met exactly. **⚖ Rev 3 (critic): the commit is REF-LESS, definitively** — the earlier "or under `refs/ora/exec-review-tmp/<id>`" alternative is dropped: a hard crash before `finally` would leave a permanent ref pinning a full snapshot of the user's tree (including possibly-sensitive uncommitted content) in their repo forever, while the ref-less object is unreachable and GC-collects. `git worktree add --detach <raw-sha>` accepts a ref-less commit (the worktree's own HEAD file keeps it alive for the worktree's lifetime); after `remove`+`prune` it is GC-garbage. Crash residue is therefore bounded: an unreachable object (GC-swept) + a stale scratch worktree dir (orphan-pruned at next actuator start; stealth turns never reach the actuator — `run_loop` returns first on stealth).

### 3.2 Containment + never-touch-user-HEAD guarantee

- Worktree root: `runtime_paths.SCRATCH_DIR/exec-review-worktrees/<short-id>` — runtime-paths-derived (portability amendment), passes SEC-2 (not an ancestor of any private root), pre-flighted through `sandbox_worktree_unsafe` (SBPL-char guard included; refuse honestly + fall back to the deferred marker if the scratch path is SBPL-unsafe).
- Git operations that touch the user's repo are confined to: ref-free plumbing reads, the throwaway-index temp commit (proven idiom, Phase 6), `worktree add/remove/prune` (which write `.git/worktrees/` METADATA — disclosed in the packet as a repo-metadata touch; never HEAD, never index, never tracked files). New containment checks use `runtime_paths.within_base` (case-normalized), not a new `startswith`.
- Sandbox: the existing profile with `allow_write_repo=True` scoped to the worktree; private roots re-denied under it; network deny enforced or the check refuses (unchanged enforce-or-refuse).
- Failure = honest degrade: any lifecycle failure (add/commit/timeout) falls back to the CURRENT behavior (`_record_deferred_mutating`, reason updated to name the actual failure) — the actuator never turns a working degrade path into a crash.
- Concurrency honesty: the delta_commit snapshots the live tree at capture time; on repos with external mutators (vault autocommit, Obsidian linter) foreign churn can ride in — recorded via the existing `dirty_hash` + a `delta_attribution: approximate` note in `review_dirty_diff` mode (already the landed semantics of that mode; no new claim of exactness).

### 3.3 Gating + placement in the loop

Runs inside `run_capture`'s existing mutating-split (:320-329): when `mutates:true` required checks exist AND the loop is live, attempt the isolated run instead of recording deferred. Master gate remains `ORA_EXECUTION_LOOP` (the actuator is dead code while the loop is OFF, exactly like the rest of run_loop); a kill-switch env `ORA_EXEC_REVIEW_MUTATING=off` restores the deferred-marker behavior (OQ-7). Both the worktree-run results and any fallback-deferral are observed `evidence_check` events (existing recording — `run_check` fires it for every outcome).

**⚖ Rev 3 — second routing condition (critic BLOCKER: the vault family was unreachable as designed).** The actuator as originally scoped routed ONLY `mutates:true` checks into the worktree — but a SEC-2-protected repo (the vault: `repo_root` equal-to/ancestor-of a sensitive root) has its NON-mutating checks refused in-place too ([evidence_runner.py:522-543] pre-flight), so every vault-catalog check was structurally unrunnable: refused live, never routed isolated. Fold: `run_capture` gains a `requires_isolated_worktree(repo_root)` predicate (true when `sandbox_worktree_unsafe(repo_root, …)` would refuse the repo in-place) — when true, ALL of that repo's required checks (mutating or not) route through the §3.1 worktree; when false, only `mutates:true` checks do (unchanged). The Chunk-B lifecycle API therefore accepts non-mutating batches from day one — this is a Chunk-B API requirement, not a Chunk-C afterthought, and is why C depends on B.

### 3.4 What "closes the `unmerged_guarantee: PARTIAL` note" honestly means (OQ-9)

The PARTIAL note fires because a committing executor lands commits ON THE USER'S BRANCH — no post-hoc branch can un-merge them; only executing in isolation from the start can. Phase 8: (a) delivers the worktree substrate + makes `mode="clean_worktree"` REACHABLE — a caller that declares `context_pkg["exec_review_mode"]="clean_worktree"` and actually runs its executor in an isolated worktree (programmatic/recipe executors: future MSI runs, evaluation harnesses) gets the FULL §13 guarantee end-to-end (capture, mutating checks, escalation branch all against the isolated tree); (b) narrows the note: it now distinguishes "full isolation available but this run executed in place (live chat turn)" from the old blanket "requires Phase 8". Phase 8 does NOT silently reroute live chat-turn tool writes into a worktree — that would be a semantic change to every user turn and is out of scope. The judge should confirm this reading of "closes".

### 3.5 Known limitation, v1: git-invoking checks inside the sandbox

A linked worktree's `.git` file points at the main repo's denied `.git/worktrees/` + commondir, so a catalog check that runs `git` INSIDE the sandbox fails (§1.3). v1 ships WITHOUT a profile carve-out: typical catalog checks (build/test/lint/typecheck) don't invoke git; one that does will fail-and-record (observed, honest). A narrow read-only carve-out for `<repo>/.git` is the documented follow-up (OQ-8) — it re-exposes repo HISTORY to the check, which deserves its own judged look, not a rider.

### 3.6 Scale guard (vault-class repos)

`create_isolated_worktree` supports `sparse=<paths>` (`worktree add --no-checkout` + `sparse-checkout set` + `checkout`) and a `timeout=` override on `_git` (default stays 30s; the actuator passes a larger bound). Vault-family checks (§4.2) are designed to need only changed files + `git ls-tree` metadata (title universe read from the object DB, not the filesystem) so the vault worktree stays small. A repo whose materialization exceeds the bound → honest deferral marker (never a half-built worktree left behind — `finally` removes). **Rev-1 precision (hand-critique):** at vault scale the expensive AND race-prone git op is the `_tree_commit_at` temp commit (`add -A` over the working tree), NOT `worktree add` alone — `add -A` walks every changed/untracked path and races the vault autocommit's ≤15-min rebase+push. The `timeout=` override (§3.1) and the honest-deferral fallback (§3.2) therefore cover the temp-commit step explicitly, and `delta_attribution: approximate` (review_dirty_diff mode) is stamped whenever foreign churn could have ridden the `add -A`.

### 4.3 Deploy+probe family — probes are instrumented READS, not sandboxed subprocesses

Declared honesty, never invented capability.
