## Lessons learned from Chunk 0 (fold into every future chunk)

1. **Anchors go stale fast — always re-verify against live HEAD, never trust a design doc's cited line numbers.** `~/ora` moved 9 commits during Chunk 0's own design→implement→review cycle, and 3 more between Codex's round-2 approval and the actual merge. Re-fetch and diff every upstream commit against every function the chunk touches (not just filenames — actual line ranges) before both the implementation worktree creation AND the final pre-merge rebase. A clean rebase is necessary but not sufficient — confirm zero semantic overlap too.
2. **`ORA_HOME` must be exported when running the test suite from any worktree other than `~/ora` itself.** `server.py`'s `WORKSPACE` constant (and others) silently default to the literal `~/ora` otherwise, which can pull the live checkout's copy of a same-named module into a worktree's test run and produce confusing false results in either direction. `export ORA_HOME="$(pwd)"` before every `unittest discover` invocation from a worktree. (A related fix landed upstream as PR #216 during Chunk 0; the env-var requirement itself is a usage discipline, not something code can fully paper over.)
3. **Enumerate every production entry point a change needs to cover, not just the one the design doc's ground-truth section happened to describe.** Chunk 0's design doc anchored entirely on `server.py`'s `_pipeline_stream` (the Flask chat server) and initially missed `boot.py`'s `run_pipeline` (the CLI/terminal interface) — a second, independent call path into the same pipeline. An adversarial self-review caught it before Codex saw it, but it should have been caught at design time. For Chunk 1 specifically: framework trace propagation, verbatim capture, and config snapshots all need to work whether the framework/gear run was dispatched via the server or via `run_pipeline`.
4. **Run an adversarial self-review (multiple independent lenses, each finding verified against actual source) before ever handing a packet to Codex.** Round 1 of Chunk 0 would likely have blocked on more than 2 findings if the pre-existing self-review hadn't already caught and fixed 4 issues (including the `run_pipeline` gap above) first. Budget for this as a standard step, not an optional extra — and verify every finding personally against the code before acting on it or discarding it; an unverified finding is worth nothing either way.
5. **Full-suite parity means TWO fresh runs (baseline + implementation) at the same commit, both with `ORA_HOME` set, diffed as sorted FAIL/ERROR lists — not just "the new tests pass."** Do this once after implementation, and again immediately before the final merge if any rebase happened in between (parity can silently rot if upstream changed shared fixtures/state, even when the diff itself has zero overlap).
6. **Codex's code-review gate can BLOCK, not just approve.** Build the fix-verify-redeliver loop into the plan from the start rather than treating approval as the only expected outcome. Both P1s Codex caught in round 1 were real, narrow, and exactly the kind of thing that's easy to miss when instrumenting many branch points by hand (a tag-lookup reading stale/absent disk state instead of the live request value; a re-kind assignment missing on one specific held-turn branch) — line-by-line re-verification of every branch touched, not just spot-checking, is what round 2 needed.
7. **The vault repo requires an explicit go-ahead before any file edit — do not fold vault commits into `~/ora`'s standing "commit/push/merge by default" authorization.** They are different repos with different standing instructions; ask before touching the vault, every time, even for a purely factual documentation update that mirrors already-approved code.
8. **A held/paused turn is not the same as a "short-circuit."** Chunk 1's pin/archive semantics and Chunk 3/4's resume/re-execution work will each introduce their own new terminal states or branch points — apply the same discipline Chunk 0 needed: enumerate every return/exit site by hand, decide its honest classification, and write a test that would fail if a future refactor silently changed that classification.
