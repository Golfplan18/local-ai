## Round 1 → BLOCK → round 2

Codex blocked the round-1 packet with 3 findings: two P1 (real bugs, both confirmed against source and fixed here) and one P2 (branch had drifted 9 commits behind `origin/main`, touching all 3 files this patch also touches — rebased, re-verified, re-tested here). Full account below.

### Codex block finding #1 (P1) — first-turn stealth/private tag ignored, FIXED

Confirmed exactly as reported. `_pipeline_stream_impl`'s turn-head stealth setup re-derives the conversation's tag from disk (`get_conversation_tag(panel_id)`) rather than using the request's own `conversation_tag` parameter. `get_conversation_tag` returns `""` when no `conversation.json` envelope exists yet (confirmed by reading its docstring/implementation) — which is exactly the state of a **brand-new** conversation's first turn. So a first-ever message the client marks stealth or private still opened a trace (`stealth=False` reached `start_trace`), and — new in this round — the trace's `trace_ref` would additionally have been threaded into the conversation-manifest line and `conversation.json`'s assistant turn, since that's this chunk's whole new surface. Same pattern existed at both clarification endpoints (resume/skip), reading disk instead of the paused turn's own stored `conversation_tag`.

**Fix:** persisted envelope tag wins when present (preserves the existing "immutable after first save" convention for an ongoing conversation); falls back to the request's own tag (main path) or the paused turn's stored tag (`pending.get("conversation_tag")`, both clarification endpoints) only when no envelope exists yet. Three call sites fixed: `server.py` main turn-head, `clarification_respond`, `clarification_skip`. `_direct_stream`'s own analogous tag-read (used for its tool-event stealth suppression) was NOT touched — it already prioritizes the request tag over the disk read (`_ds_tag = conversation_tag; if not _ds_tag: ... get_conversation_tag(...)`), which doesn't exhibit the reported defect (it never silently ignores a present request tag); flagged here for visibility rather than changed, since Codex's finding named 3 specific sites and this one behaves differently already.

Regression tests: `test_first_turn_stealth_tag_honored_when_no_envelope_exists` (mocks `get_conversation_tag` → `""`, passes `conversation_tag="stealth"`, asserts zero trace files) and `test_persisted_envelope_tag_wins_over_differing_request_tag` (mocks `get_conversation_tag` → `"stealth"` with an empty request tag, confirms the envelope still wins — proves the fix didn't just flip the bug in the other direction).

### Codex block finding #2 (P1) — direct-fallback risk hold finalizes as `direct`, not `risk_hold`, FIXED

Confirmed exactly as reported: `_direct_stream`'s own risk-gate hold branch (reached only via `_pipeline_stream_impl`'s fallback_to_direct path, which had already stamped `turn_state["kind"] = "direct"`) returned the hold reply without re-kinding `turn_state`. Since `direct` is a member of `SHORT_CIRCUIT_KINDS`, a held turn finalized as `terminal_status: short_circuit`, `trace_kind: direct` — losing the fact that it was actually held for risk reasons, the same honesty gap design-gate condition 1 exists to close.

**Fix:** `turn_state["kind"] = "risk_hold"` set immediately before the hold response is yielded, guarded by the existing `if turn_state is not None:` (the `/direct` slash-command call site still passes no turn_state and is unaffected). Regression test: `test_direct_stream_risk_hold_rekinds_from_direct` (mocks `get_endpoint` to succeed and `risk_gate.evaluate_hold` to return a hold, asserts `turn_state["kind"] == "risk_hold"`).

## Decisions taken (judge attention here)

1. **Q1 mechanics — wrapper delegation instead of re-indenting 600 lines.** The single try/finally lives in a thin `_pipeline_stream` wrapper delegating to `_pipeline_stream_impl(…, turn_state=dict)`. Identical semantics to wrapping the body (GeneratorExit propagates through `yield from`; inner `finally` blocks — cost summary — run before the wrapper's finalize, so `cost-summary.json` is on disk when the finalizer scans); the diff stays reviewable. `turn_state` is a dict rather than bare locals because the kind/status assignments must cross the wrapper/impl boundary and reach `_run_pipeline_from_step2`. **One casualty:** a pre-existing pinned test located `_pipeline_stream`'s body by slicing from its `def` to the next top-level `def`; after the split that window captures only the wrapper. Fixed by pointing the test at `_pipeline_stream_impl` instead (same file, one-hunk change) — the invariant it protects (stealth setup before every short-circuit) is unchanged and still holds. Same wrapper-delegation pattern applied to `orchestrator/boot.py::run_pipeline` (finding #3).
2. **Explicit gear/completed signals from `_run_pipeline_from_step2` (and its `boot.py` twin).** Gear-1/2 pipeline turns never write `step-health.json`, so a disk-only derivation would misclassify every completed gear-1/2 turn as `abandoned`. `turn_state["gear"]` is set at gear dispatch (and again on degradation fallback) and `turn_state["status"]="completed"` at the pipeline-complete point, for all gears. Status precedence in the finalizer: error > paused > completed/step-health > short_circuit > abandoned; a crash after the completed signal still finalizes `error` because the wrapper overwrites the hint on `BaseException`.
3. **Mid-pipeline risk holds re-kind to `risk_hold`** (both the tier hold and the criteria hold, in both `_run_pipeline_from_step2` and `run_pipeline`) — a held turn is an intentional stop, not an abandoned pipeline run.
4. **`direct` expects the step1 files; other short-circuit kinds expect `[]`; `clarification_pending` expects `[]`** (paused after step1 is a legitimate end state — its step1 files appear as observed; nothing is "missing" on a pause). `clarification_resume` expects the gear table minus step1 (resume reuses the stored step1 dict — design D1 note).
5. **`derived_artifacts` as a third manifest field** (condition 5, "classify them separately"): `step-health`, `step-visual-hook`, `step-visual-emissions`, `cost-summary` are recorded as present but can never appear as steps. Markdown siblings and JSONL logs are neither steps nor derived artifacts.
6. **`chat` → `chat-gear<N>` refinement at finalize; bare `chat` survives when the turn died before gear selection** — honest "got past step 1, never reached dispatch". This refinement is now gear-precedence-corrected (finding #1): the gear used is whatever `step-health.json` says actually ran, not the pre-dispatch prediction, when the two disagree.
7. **`redaction_level` from a new optional `conversation_tag` param on `start_trace`** (`"private"` → `private`, else `default`). PROVISIONAL per the flag-provisional convention: the two-level mapping is a placeholder until Chunk 2 defines viewer redaction semantics. Now threaded from both `server.py` call sites AND `boot.py::run_pipeline` (finding #6).
8. **Skip endpoint kind = `clarification_resume`** (a skip is a resume without answers; `metadata.json` `raw_input` records `[clarification-skip]`).
9. **Fixed in passing (pre-existing):** the clarification endpoints' `_resume_tag`/`_skip_tag` were assigned only inside a try block but read after it — an early import failure would have raised `NameError` at the later `conversation_tag=… or _resume_tag` read. Now initialized before the try. Also Q2 as directed: both endpoints now compute `cost-summary.json` best-effort.
10. **Manifest "open" as a terminal residue is meaningful:** a turn whose process died so hard the finalizer never ran leaves `terminal_status: "open"` — itself an honest signal, documented in the vault draft.

## Condition compliance map

- **Condition 1 (status-hint-aware errors):** every catch-yield-error-return site sets `turn_state["status"]="error"` before returning — runtime-command failure, no-endpoint, resolution failure, framework elicitation failure (continuation and start), framework command failure and parse error, `_run_pipeline_from_step2`'s no-active-endpoint, and (after finding #4) `_direct_stream`'s own no-endpoint check when reached via the fallback_to_direct branch. Uncaught exceptions and `GeneratorExit`-with-work-done are distinguished by the wrapper (error vs abandoned/completed). `run_pipeline`'s mirror set is covered identically.
- **Condition 2 (paused, never abandoned):** all three pause sites set kind `clarification_pending` + status `paused`.
- **Condition 3 (explicit trace_ref channel):** dedicated in-band `trace_ref` event from the generator; `_invoke_pipeline` captures it and passes it to `_save_conversation` (sync call + manifest jsonl line) and `_persist_turn_spatial_state` (daemon-thread kwargs) → `save_turn_spatial_state` → assistant turn. Clarification endpoints pass their own refs through the daemon-thread `kwargs`.
- **Condition 4 (persisted parent refs):** all three pause sites store `trace_ref` (the paused turn's own ref) in `_pending_clarification`; the manual continuation path and both endpoints read it into `parent_trace_ref`.
- **Condition 5 (filtered actual_steps):** `_scan_turn_dir` splits steps vs derived; required tables are conservative (Q3 split) — verifier cycles, step4.5, step5.5, step6_5, web consultation are observed-only. Two additional legitimate-but-reduced-footprint completions (single-analyst fallback, external-consolidation handoff) are now contingency-aware rather than merely "observed" — see finding #2.

## Adversarial pre-check

Run as a multi-lens Workflow (correctness/control-flow, design-condition compliance, persistence-surface safety), each lens finding independently, findings queued for adversarial verification. The account hit its monthly spend limit partway through: the persistence-safety lens and every verification pass failed to run before completing. Two lenses (correctness, design-condition compliance) finished and returned 9 raw findings (2 exact duplicates across lenses). I verified every one of the 9 myself directly against the source (grep + read, no further agent spend) rather than trust an unverified raw finding or discard it for lack of automated verification.

**Confirmed and fixed (4):**

1. **CRITICAL — `run_pipeline` (boot.py) never finalized.** The design's own ground-truth section anchored entirely on `server.py`'s `_pipeline_stream`; `run_pipeline` — the CLI/terminal-interface entry point, and the direct call target of test files like `trace_smoke_test.py` and `test_risk_gate_pipeline.py` — opens a trace via `start_trace` but `finalize_manifest` was never called anywhere in `boot.py`. Confirmed by grepping every `finalize_manifest` call site in the repo before the fix: exactly 3, all in `server.py`. Every CLI-invoked turn's manifest was permanently stuck at `terminal_status: "open"` — indistinguishable from a mid-turn crash even on a normal, correct completion. **Fixed:** the same wrapper-delegation pattern as `server.py` (task in "Files changed" / boot.py).
2. **MAJOR — `finalize_manifest`'s gear derivation only consulted `step-health.json` when the caller passed `gear=None`.** `run_gear4` (boot.py) has two internal, legitimate, documented fallback branches to `run_gear3` (single/both analyst streams unrecoverable — confirmed by reading both call sites) — the caller stamps `turn_state["gear"]=4` before dispatch and never learns the degrade happened. Since the explicit stale `4` always won, a turn that actually completed as gear 3 reported `"gear": 4` and the gear-4 required-step table, permanently "missing" 5-7 steps it never should have expected. **Fixed:** `step-health.json` (the actual-execution ground truth, written last by whichever gear function really completed) now wins whenever present and readable; the caller's hint is used only when step-health is absent (gear-1/2 turns).
3. **MAJOR — two legitimate reduced-footprint completions weren't accounted for in the required-step tables.** Confirmed by reading both call sites: gear-3's single-endpoint fallback (`boot.py` ~11267) writes only `step3-single-analyst-fallback` and returns — a *stable per-installation state* for any config with just one model in gear 3's depth/breadth slot, not a transient error, meaning it would have shown 3 false "missing" steps on *every single gear-3 turn, forever*, for such installations. Gear-4's external-consolidation-handoff branch (`boot.py` ~12668) writes only `step7-external-consolidation-handoff` and returns, also a legitimate designed-in shortcut. **Fixed:** a `_CONTINGENCY_SATISFIERS` map — when one of these markers is observed, it replaces (not supplements) the specific required steps it makes moot, rather than the manifest quietly reporting a healthy completion as broken.
4. **MINOR — `_direct_stream`'s own "no endpoint" path wasn't wired to `turn_state` at all.** Reachable via `_pipeline_stream_impl`'s fallback_to_direct branch (which already set `kind="direct"`) if the active endpoint disappears in the window between that branch's own earlier endpoint check and `_direct_stream`'s independent re-check (e.g. a concurrent settings change during Step 1's model call) — the turn produces no response but finalized as `short_circuit`, not `error`. **Fixed:** optional `turn_state` param, set at that one site; the *other* call site (`agentic_loop_stream`'s `/direct` command dispatch) passes no turn_state and is unaffected — see noted-not-fixed #2 below for why that path is out of scope here.

**Noted, not fixed (judgment calls surfaced for Codex, not silently overridden):**

1. **Verifier-cycle-1 is "observed-only," not required**, per the design-gate's own Q3 modification — a reviewer raised that this leaves zero manifest protection against a silently-skipped adversarial verification stage. This is a direct critique of a judge-approved tradeoff from this same design gate; I did not unilaterally reverse it. Surfacing for awareness in case the judge wants to revisit Q3.
2. **The `/direct` slash command bypasses tracing entirely** (`agentic_loop_stream` routes straight to `_direct_stream` when `use_pipeline=False`, never touching `_pipeline_stream`/`start_trace`) — a turn's `trace_ref` ends up `null`, bit-for-bit identical to a stealth turn or `ORA_PIPELINE_TRACE=off` on disk. Confirmed this is **pre-existing behavior**, unchanged by Chunk 0 (`_direct_stream` never called `start_trace`, before or after). Making this path traced is a behavior change (opening a trace where none existed) beyond "make existing traces honest" — left as a known scope boundary for the judge to decide, not fixed silently.
3. **GeneratorExit-disconnect safety isn't exercised by the live `/chat`/`/chat/multipart` routes today** — both drain `_pipeline_stream` synchronously inside `_invoke_pipeline`'s plain `for` loop (confirmed: the repo's only two `stream_with_context(...)` wraps are the clarification endpoints' own generators, neither of which streams `_pipeline_stream` itself). The wrapper's exception-safety (an uncaught exception anywhere in the impl still finalizes `error` via the `finally`) is real and exercised today regardless; the GeneratorExit branch specifically matters for future true-streaming callers and the test that calls `gen.close()` directly. Not a code defect — an accuracy note on how the design doc frames the wrapper's benefit.

## Parity

Two things had to be worked out before parity was trustworthy, neither of them a Chunk 0 code bug:

1. **Environment gap:** running the suite from a worktree other than `~/ora` without exporting `ORA_HOME` lets `server.py`'s `WORKSPACE` constant (which defaults to the literal `~/ora` absent that env var) push the *live checkout* onto `sys.path` ahead of the worktree, silently swapping in the wrong copy of modules like `conversation_memory` for any test that does a bare `import`. `start.sh` always exports `ORA_HOME` in real operation; a bare `python3 -m unittest discover` invocation does not. Flagged separately (a fix for this has since landed upstream as part of the 9-commit drift in the Rebase section above); every run below exports `ORA_HOME` to the worktree under test.
2. **The rebase** (previous section) meant the baseline needed rebuilding at the new SHA rather than reusing the pre-rebase numbers.
