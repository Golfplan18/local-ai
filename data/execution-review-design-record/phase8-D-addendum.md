## 2. Generic seam (ora, project-agnostic) — `record_program_run`

Only ONE genuinely-new generic seam (the `invoke_chat` one is dropped, §1.1). A new small module/function `execution_review.record_program_run(...)` (name per design §5; likely a thin new `orchestrator/execution_review.py` or a function in `execution_loop`) that runs the packet-build + declared-lane fill + redaction + persistence gauntlet for a programmatic, non-terminal run. **Contains no MSI knowledge.**

### 2.1 Signature + contract (⚖ Rev-3, binding)
`record_program_run(*, events_path, output_text, repo_root=None, enforcement_model, risk_tier=None, output_type="execution", producer_claim=None, trace_dir=None, conversation_id=None, stealth=False, runner=None) -> str|None`.
- **Signals FOLDED from the run's own event log** — `fold_route_observed(events_path, output_text=output_text)` (whole-file mode). NEVER caller-narrated (§16-3). An empty/absent log folds to no-signals + an `instrumentation: none` stamp (disclosed blindness, not a caller-suppliable green).
- **Evidence lanes filled ONLY by the registered fillers** — `record_program_run` attaches the target repo's `standing:true` declared lanes by the landed Chunk-C seam (§1.6): **⚖ Rev-3 (judge P3) — build the declared-lanes list from `catalog.recipes` directly** (`[{lane, target, recipe: name} for name, r in catalog.recipes.items() if r.standing and r.lane and r.target]`), NOT from `lanes_from_catalog`, which DROPS the `standing` field so its output cannot be filtered (alternatively extend `lanes_from_catalog` with a `standing_only=` flag — the impl packet picks one). Stash that list as `context_pkg["evidence_contract"]["lanes"]`, pass the `context_pkg` into `build_execution_packet` so `route_lanes(declared=…)` appends them DECLARED-EMPTY; THEN `fill_declared_lanes(packet, context_pkg={"repo_root": repo_root, …}, trace_dir=trace_dir, runner=runner)` runs the deploy_probe filler against the matching recipe. (`lanes_from_catalog` alone attaches nothing, and `fill_declared_lanes` only fills lanes already on the packet — so the build step is load-bearing.) Never accepts lane verdicts as caller data.
- **Caller free-text → `producer_claim`** — rendered LAST, labeled unverified (§12). Never a signal or a lane.
- **`enforcement_model` caller-MANDATORY, no default** (approved condition) — validated against `tool_events.ENFORCEMENT`; a missing/invalid value REFUSES (returns None + stamps a failure) rather than inheriting a false `in_harness`. Set onto the built packet via `populate_loop_fields(execution={"enforcement_model": …})` (the whitelisted override seam, §1.5). The honest exception the design names: the enforcement REGIME is the integrator's knowledge (not derivable from the log), so it's caller-declared — but it can only OVERSTATE what the events then fail to corroborate, and vocabulary-validation bounds it.
- **Persist AND write the trace-local packet — ⚖ Rev-3 (judge P2).** `persist_packet(packet, sig={"max_sensitivity": <from the fold>}, trace_dir=trace_dir, stealth=stealth)` only DECIDES the durable tier + writes the ledger/note WHEN promoted — it does NOT write the trace-local `execution-packet.json`. So `record_program_run` calls `persist_packet` THEN `write_packet(packet, trace_dir)` (mirroring the loop at `execution_loop.py:1629`), so a `git_only` or `instrumentation: none` run still leaves the trace-local packet even when nothing is promoted durably. `set_turn_context(conversation_id=…)` is set first (§2.2) so the durable note is conversation-scoped + stealth-purgeable.
- **Never raises** (the whole-module discipline); stealth → no durable write.

### 2.2 Where the run's events come from (the fold source + atomicity + correlation, one move)
The caller (MSI's `invoke_real_gear4`) gives the run its OWN per-run trace-dir and calls `tool_events.set_turn_context(trace_dir=<per-run>, conversation_id=<run-id>, risk_tier=…)` at the START — so EVERY event the run emits (across the whole call, same thread → the `set_turn_context` ContextVar stays active) routes to `<per-run>/tool-events.jsonl`, and `record_program_run(events_path=<per-run>/tool-events.jsonl)` folds from exactly that file.

**⚖ Rev-3 — the recording point is at the END, after the FINAL output is selected (judge P1).** `invoke_real_gear4` does NOT return `run_gear4`'s output directly — after `boot.run_gear4` it runs one of four consolidation paths (`corpus` fallthrough, `integrate_best`, `select_best`, `analyzer_section_best`), and the last three make ADDITIONAL `chain_invoke_default`→`_call_openrouter` model calls (`msi_run_gear4.py:1601/1614/1622` returns) and return a DIFFERENT final prose. So recording at `~1571` (before consolidation) would fold an INCOMPLETE log and attest the wrong (pre-consolidation) output — a "narrated, not observed" violation for the actual shipped prose. **Fix:** `record_program_run` fires once, at the end, on the FINAL selected `prose`, for every consolidation mode. Implementation shape: capture the final output into one variable and record before `return` (a `try/finally` on the successful path, or a single post-selection call before each return), so the complete per-run log is folded and the FINAL prose is `output_text`/`producer_claim`. A `Gear4Halt` / strict-health-hold run raises before selection (`:1586/:1588`) → no shippable output → NO packet (honest: a halted run has nothing to attest). **What the per-run sink then holds:** run_gear4's in-harness `model_call` events (via `boot.call_api_endpoint`, the MSI OpenRouter patch wraps it) PLUS the consolidation's `_call_openrouter` boundary events — a mix. The folded packet stamps `enforcement_model: boundary_only` (the caller-declared REGIME — the bare-subprocess program run Ora cannot per-call-gate), which honestly UNDER-claims relative to the per-event `in_harness` model_call stamps in that log (never overclaim, §7 — the fold reads the per-event axes, the packet declares the outer regime). `invoke_real_gear4` already builds a per-run trace-dir (`_trace_dir_for(label, user_prompt)`, `msi_run_gear4.py:1526`), which seeds both the `set_turn_context(trace_dir=…)` at the start and the `events_path` at the end. This single per-run-sink choice resolves all three of: the §16-3 fold source, the §6-iii atomicity concern (per-run files never contend), and the correlation gap (distinct `conversation_id` per run). `record_program_run` derives `repo_root = dirname(ORA_PROJECT_ROOT)` (the astro repo, where `.ora/` + `src/content/articles/` live); `msi_run_gear4` doesn't read `ORA_PROJECT_ROOT` today (a new read).

- **(i) MSI loop reach — RECORD, not the converge/escalate loop (scoped out LOUDLY, silence is not an option).** `run_gear4` bypasses the Phase-6 terminal entirely (grep-verified: the terminal hangs off `run_pipeline`/`server`, never `run_gear4`); wiring the loop = MSI itself calling `run_loop` around `run_gear4`'s output — a genuine build, not a flag. **Decision: Chunk D wires `record_program_run` (record + declared-lane fill + provenance + persistence), NOT the loop**, because (a) the live gear-reinvocation actuator is unwired system-wide (`actuator=None` everywhere — a Phase-6/7 follow-up, explicitly NOT Phase 8); a loop with no actuator only escalates; (b) MSI is zero-manual-labor async — a failed verify would escalate to the Paused queue, which NO MSI systemd process monitors, so the "escalation" would be a silent dead-end; (c) `record_program_run` already delivers the observability the loop would (packet + provenance map + deploy_probe post-hoc evidence + honest `enforcement_model` + tiered persistence). Closing the loop over MSI is a named follow-up gated on the live actuator landing.
- **(ii) Publish irreversible-gate posture — boundary-observed + tier-stamped, NO per-article human gate.** A published article is the spec's canonical irreversible action, but (scout-confirmed) publishing is NOT classified/gated today, and zero-manual-labor FORBIDS a per-article human gate. **Decision: do NOT add a GATING irreversible manifest entry** (it would block MSI publishing). The honest record: a publish boundary event at the push/harvest seam (with the `external_write`/`irreversible` MUTABILITY on that tool-event) + the packet stamped `output_type: execution` + a `risk_tier` reflecting the irreversible/high-consequence nature (`irreversible`/`high-risk`) + `enforcement_model: boundary_only` (per-call gating impossible on a bare-subprocess push) + the deploy_probe lane as the POST-HOC evidence. (`output_type` is the locked {unknown,text,execution} hint — the irreversibility rides `risk_tier` + the event's mutability axis, not `output_type`.) The gate question is answered honestly (observed + recorded, not enforced) rather than left unasked.
- **(iii) Concurrent-process sink atomicity — per-run sinks.** The global sink/ledger append is atomic only below `PIPE_BUF` (4096); lines exceed it and have no lock, so 14 concurrent MSI units on ONE global sink can tear + are indistinguishable (`conversation_id=None`). **Decision: each program run writes its OWN per-run sink** (`set_turn_context(trace_dir=<per-run>)` → `<per-run>/tool-events.jsonl`), so concurrent runs never contend and `record_program_run` folds from an isolated file (§2.2). For the `_call_openrouter` boundary events on bare systemd units that never reach a program-run trace-dir, the recipe sets a per-process `ORA_TOOL_EVENTS_PATH` (per-unit sink) OR a distinct `ORA_CONVERSATION_ID` in the systemd unit env — the implementation packet picks per-unit sinks (simplest, lock-free). No change to the global-sink write path itself (out of Chunk-D scope; recorded as a latent ora-core hardening — cap/lock the ledger line — for a separate task).
